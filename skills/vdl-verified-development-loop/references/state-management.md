# State management

Bug mode adds a diagnosis phase before draft approval. The main agent emits `diagnosis.started`, records each investigator report as diagnosis evidence under `.verified-development-loop/evidence/PLAN/`, and emits `diagnosis.completed` only after recording its actual result. The bug Plan and its Task link that evidence; approval, TDD entry, and completion require the linked, reproduced code diagnosis. At most two reports are allowed for one Plan ID. A non-reproduced, non-code, or still low-confidence diagnosis cannot activate a bug Plan. Feature records omit `mode` or use `feature` and follow the existing transitions below.

`.verified-development-loop/specs/drafts/` and `.verified-development-loop/plans/drafts/` hold unapproved Markdown records with matching IDs. Approval moves the Spec to `.verified-development-loop/specs/active/PLAN.md`, the Plan to `.verified-development-loop/plans/active/PLAN.md`, and creates `.verified-development-loop/tasks/active/TASK.md`; the Plan links its active Spec via `spec_file`. A blocked Task leaves its Spec and Plan active. Completing the Plan moves the Spec to `.verified-development-loop/specs/completed/PLAN.md`, Plan to `.verified-development-loop/plans/completed/PLAN.md`, and updates `spec_file`. Each Markdown file contains embedded JSON state for the scripts; its visible text is generated from that state. Revise a draft through a fresh proposal, not by editing generated text or lifecycle metadata manually.

After current PASS verification and review, `qa` records PASS or FAIL with a report from the independent `qa_tester`. QA evidence links the current verification and review and carries the same code fingerprint. A new verification, review, or code change invalidates previous QA PASS. Normal Task completion requires current PASS verification, current PASS review, current PASS QA, explicit attestation of every task criterion, all its error records RESOLVED, and a nonempty linked `completed` report. The code fingerprint in all three evidence records must still match the repository. Normal Plan completion requires all linked tasks completed, no active or blocked task, all plan errors resolved, and explicit attestation of every plan criterion. The separate accepted-error completion requires an explicit human decision, current verification/review/QA evidence, only classified non-Blocker errors, and a linked `completed-accepted` report; it does not weaken normal completion.

Blocked tasks stay in `.verified-development-loop/tasks/active/` with `status: blocked`; their plan remains in `.verified-development-loop/plans/active/` with `execution_state: waiting_human`. QA code failures and repeated review errors can use up to three fix rounds; the same confirmed error remaining after the third fix stages a blocker and prevents more fixes. The main agent writes a `blocked` report before `block-task` performs the transition. QA environment failures may be rerun without increasing the fix counter. Spec or uncertain QA findings wait for a human decision and, if revised, a newly approved Plan ID. The main agent reports why and waits for a human decision. The report's four standard options are suggestions, not an exhaustive decision list. A human may approve a new Plan/Task with a different approach, revise the Spec or Plan, accept eligible remaining errors, cancel, or defer the decision. Accepted-error completion writes a new report and returns the Plan to `running` when no blocked Task remains. Do not erase prior attempts or reset the existing counter. The current CLI has no retry or unblock command: a blocked Task cannot run another fix round, and a Task at 3/3 cannot receive a fourth. Further repair work needs a new approved Plan ID.

Every task ending links its newest report through `latest_report` in the Task Markdown and embedded state. The reports live in `.verified-development-loop/reports/` beside `tasks/` and `plans/`; a new ending creates a new file and never overwrites an older one. The script refuses `blocked`, `completed`, and accepted-error completion without the matching nonempty report. A failed report write leaves the Task active.
