# State management

`.verified-development-loop/specs/drafts/` and `.verified-development-loop/plans/drafts/` hold unapproved Markdown records with matching IDs. Approval moves the Spec to `.verified-development-loop/specs/active/PLAN.md`, the Plan to `.verified-development-loop/plans/active/PLAN.md`, and creates `.verified-development-loop/tasks/active/TASK.md`; the Plan links its active Spec via `spec_file`. A blocked Task leaves its Spec and Plan active. Completing the Plan moves the Spec to `.verified-development-loop/specs/completed/PLAN.md`, Plan to `.verified-development-loop/plans/completed/PLAN.md`, and updates `spec_file`. Each Markdown file contains embedded JSON state for the scripts; its visible text is generated from that state. Revise a draft through a fresh proposal, not by editing generated text or lifecycle metadata manually.

After current PASS verification and review, `qa` records PASS or FAIL with a report from the independent `qa_tester`. QA evidence links the current verification and review and carries the same code fingerprint. A new verification, review, or code change invalidates previous QA PASS. Task completion requires current PASS verification, current PASS review, current PASS QA, explicit attestation of every task criterion, and all its error records RESOLVED. The code fingerprint in all three evidence records must still match the repository. Plan completion requires all linked tasks completed, no active or blocked task, all plan errors resolved, and explicit attestation of every plan criterion.

Blocked tasks stay in `.verified-development-loop/tasks/active/` with `status: blocked`; their plan remains in `.verified-development-loop/plans/active/` with `execution_state: waiting_human`. QA code failures and repeated review errors can use up to three fix rounds; the same confirmed error remaining after the third fix blocks the Task. QA environment failures may be rerun without increasing the fix counter. Spec or uncertain QA findings wait for a human decision and, if revised, a newly approved Plan ID. The main agent reports why and waits for a human decision. A human may approve a revised plan, defer, cancel, or authorize a new bounded attempt. Do not erase prior attempts or reset the existing counter. The current CLI intentionally has no automatic retry or unblock command; a revised approved plan needs a new plan ID.
