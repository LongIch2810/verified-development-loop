# Execution

## Bug mode

Use this branch only when the human explicitly calls VDL for a significant bug. If the request does not say whether it is a bug or feature, ask exactly one confirming question; handle a small one-file fix outside VDL. Read only relevant error memory and ask the human only for missing reproduction steps, environment, or expected result. Emit `diagnosis.started`, then delegate to the read-only [investigator](../agents/investigator.md) before asking the planner for a [Bug Spec](../assets/templates/bug-spec.md) and repair Plan. Treat the user's proposed cause as a hypothesis. The main agent records the report with `workflow.py record-diagnosis`; allow at most two diagnosis rounds.

Continue to planning only for `REPRODUCED`, `code`, and high or medium confidence. If not reproduced, stop and report the attempt. An ambiguous or wrong Spec/PRD goes to the human without an automatic Spec edit; an environment/configuration cause goes to the human without code changes; an uncertain cause stays blocked with its evidence. After a second low-confidence report, ask the human rather than repair by guess. The planner presents the Bug Spec, fix approach, and QA scenarios for one human approval. No application code changes before that approval. Then TDD begins with an actual Red reproduction test on unchanged code. The normal verification, independent review, QA, three-round fix limits, and blocked behavior below still apply. Record the supported root cause and completed repair in the existing error-memory format.

For each approved task, check dependencies and relevant error records. Give `tdd_coder` that Task's approved scope, Spec, acceptance criteria, `test_code`, verification commands, relevant prior errors, and the Markdown handoff requirements in [its role contract](../agents/tdd-coder.md). Check its saved report and Red/Green evidence before official verification. TDD cycles are not fix rounds.

Run `workflow.py verify --task-id ID`. Verification commands are the approved task's argv arrays and execute from repository root. The script records each command, exit code, stdout/stderr, and source fingerprint. Nonzero exits yield FAIL; missing commands or timeout yield UNVERIFIED. If a required check cannot run, use `block-task --task-id ID --reason '...'` and report it; never present PASS.

Only after verification PASS, ask the independent `code_reviewer` to inspect Spec, criteria, Git diff, current evidence, and code using the Markdown report requirements in [its role contract](../agents/code-reviewer.md). Check its saved report, then record its actual result with `workflow.py review --task-id ID --reviewer code_reviewer --result PASS|FAIL [--finding 'file:line: evidence']`. This CLI attestation cannot prove which model made the judgment. The main agent checks the child identity and reports it honestly.

Only after review PASS, give the independent `qa_tester` the approved Spec, acceptance criteria, and `qa_plan` from the Task. The tester runs the full suite, then every approved scenario against the real product, then relevant additional edge cases, and writes [the QA report](../assets/templates/template-qa-report.md) under `.verified-development-loop/evidence/TASK/`. Record the actual result with `workflow.py qa --task-id ID --tester qa_tester --result PASS|FAIL --report .verified-development-loop/evidence/TASK/report.md`. The coder's tests are not the QA oracle. If no native subagent is available, report that QA did not run; do not attest it.

On verification or review failure: `record-error` with a stable error ID and detection evidence; `start-fix` with the error ID and approach; direct `tdd_coder` to fix. If the same review found multiple distinct errors, `join-fix` adds each to the open, unverified round without increasing the task round count. Run verification again; review after PASS; then `evaluate --result resolved|persists --evidence 'observation'` for each error in that round. If review confirms an earlier error is fixed but finds a new, distinct error, prefix every new finding with its error ID, record it, then evaluate the earlier error as resolved against the current verification and failed review; the Task still cannot complete. The same confirmed error may use the remaining fix rounds; it blocks only when still present after the third fix. Do not reset rounds or start a new retry session. A third failed verification/review blocks the task.

For each QA FAIL, the main agent classifies every finding and calls `record-error --classification code|spec|environment|uncertain` with its QA evidence. Record every distinct finding from that QA run before saving the blocked report. Code error: `start-fix`, TDD coder repairs it, then fresh verification, review of the changed diff, and QA of **all** approved scenarios; call `evaluate` against the new QA result. The same code error may be repaired up to three times; a failure after the third fix blocks the Task. Spec gap or contradiction: block the Task, return to Spec and Plan with a new Plan ID, and seek human approval before changing them. Environment error: repair only the environment, rerun QA without increasing `fix_round`, then `evaluate --result persists` if still unavailable or `evaluate --result resolved` after QA PASS; keep the same error ID. Uncertain code-versus-Spec finding: block and ask the human. QA never edits application code or substitutes its own scenarios for the approved ones.

Before any task ending, complete the [human report template](../assets/templates/template-human-report.md) from actual evidence under `.verified-development-loop/evidence/TASK/`, then call `write-report --task-id ID --status completed|blocked|completed-accepted --input PATH`. The script creates a new report in `.verified-development-loop/reports/` and links it from the Task. Only the main agent writes it. Do not copy secrets or long logs into the report. Summarize the saved report to the human with its path only after the matching transition succeeds; if writing fails, report that failure and leave the Task in its current state.

When all criteria and errors are settled and current QA is PASS, save a `completed` report, then run `complete-task --task-id ID --accept 'criterion'` once per exact criterion. After all tasks, `complete-plan --plan-id ID --accept 'criterion'` for each plan criterion. A terminal failure after the third fix, or a Spec/uncertain finding, leaves a pending blocker: no further fix may start. Save a `blocked` report, then run `block-task --task-id ID --reason 'exact pending reason'`. A direct `block-task` call without a prior blocker stages that reason and requires the report before it can finish.

Only with an explicit human decision may a Task finish with remaining non-Blocker QA errors, including after `block-task`. Set each remaining error's severity with `set-error-severity --task-id ID --error-id ERROR --severity blocker|serious|minor`; save a `completed-accepted` report naming the accepted IDs, human, and date. Then run `complete-task-accepted --task-id ID --accepted-error ERROR --accepted-by HUMAN --accepted-on YYYY-MM-DD --accept 'criterion'` for each exact criterion. When applicable, use `complete-plan-accepted` after all Tasks. The normal completion commands still require all errors resolved. Do not accept a Blocker or an unclassified error.
